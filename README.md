# Hotel Booking System

Микросервисная система бронирования гостиниц. Проект реализован на Java 17 и Spring Boot с использованием Spring Cloud, PostgreSQL, JWT-аутентификации и Docker Compose.

Система разделяет управление гостиницами и номерами, обработку бронирований и маршрутизацию клиентских запросов. Для согласования операций между сервисами используется паттерн Saga с компенсационными действиями.

## 1. Архитектура

Система состоит из четырёх независимых микросервисов.

| Сервис | Порт | Назначение |
|---|---:|---|
| API Gateway | 8080 | Единая точка входа, маршрутизация запросов |
| Discovery Server | 8761 | Регистрация и обнаружение микросервисов через Eureka |
| Hotel Service | 8081 | Управление гостиницами и номерами, получение статистики и резервирование номеров |
| Booking Service | 8082 | Регистрация пользователей, авторизация и управление бронированиями |

**Взаимодействие компонентов:**

- Клиент отправляет запросы через API Gateway.
- Gateway маршрутизирует запросы в соответствующие микросервисы.
- Микросервисы регистрируются в Eureka и обнаруживают друг друга через Service Discovery.
- Booking Service координирует процесс бронирования и взаимодействует с Hotel Service.
- Каждый бизнес-сервис использует собственную базу данных PostgreSQL.

## 2. Запуск проекта

Для запуска необходимы:

- Docker Desktop или Docker Engine;
- Docker Compose;
- доступ к портам, используемым сервисами.

Устанавливать Java и Maven на хостовую систему не требуется: сборка приложений выполняется внутри Docker.

### Клонирование репозитория

```bash
git clone <REPOSITORY_URL>
cd spring_task
```

### Запуск

Из корневой директории проекта выполните:

```bash
docker compose up --build -d
```

Docker Compose собирает приложения, выполняет Maven-сборку и тесты, создаёт необходимые контейнеры и запускает сервисы вместе с базами данных.

### Проверка доступности

Eureka Dashboard:

```text
http://localhost:8761
```

API Gateway:

```text
http://localhost:8080
```

После запуска сервисы регистрируются в Eureka и становятся доступны через Gateway.

### Остановка

```bash
docker compose down
```

Для полного удаления контейнеров и данных PostgreSQL:

```bash
docker compose down -v
```

Команда с `-v` удаляет Docker volumes, включая сохранённые данные баз данных.

## 4. API

Все пользовательские запросы выполняются через API Gateway по адресу:

```text
http://localhost:8080
```

Для защищённых методов используется JWT. Токен передаётся в заголовке:

```http
Authorization: Bearer <TOKEN>
```

### Основные маршруты

| Метод | Endpoint | Назначение |
|---|---|---|
| POST | `/api/auth/register` | Регистрация пользователя |
| POST | `/api/auth/login` | Авторизация |
| GET | `/api/hotels` | Получение списка гостиниц |
| GET | `/api/hotels/{id}` | Получение гостиницы |
| POST | `/api/hotels` | Создание гостиницы |
| PUT | `/api/hotels/{id}` | Обновление гостиницы |
| DELETE | `/api/hotels/{id}` | Удаление гостиницы |
| GET | `/api/rooms/hotels/{hotelId}/rooms` | Получение номеров гостиницы |
| POST | `/api/rooms` | Создание номера |
| GET | `/api/bookings/me` | Получение бронирований текущего пользователя |
| POST | `/api/bookings` | Создание бронирования |
| GET | `/api/bookings/{id}` | Получение бронирования |
| POST | `/api/bookings/{id}/cancel` | Отмена бронирования |

Операции управления гостиницами и номерами доступны пользователям с ролью ADMIN. Просмотр данных и работа с собственными бронированиями доступны авторизованным пользователям с соответствующими правами.

## 5. Демонстрационный сценарий

Ниже приведён основной сценарий проверки системы: авторизация, получение гостиниц и номеров, создание бронирования, получение результата и отмена.

### Шаг 1. Авторизация

Запрос:

```http
POST http://localhost:8080/api/auth/login
Content-Type: application/json

{
  "username": "demo-user",
  "password": "DemoUser123!"
}
```

Пример через curl:

```bash
curl -X POST http://localhost:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"demo-user","password":"DemoUser123!"}'
```

В ответ возвращается JWT:

```json
{
  "token": "<JWT_TOKEN>",
  "username": "demo-user",
  "role": "USER"
}
```

Полученный токен используется в последующих запросах.

### Шаг 2. Получение гостиниц

```http
GET http://localhost:8080/api/hotels
Authorization: Bearer <TOKEN>
```

```bash
curl http://localhost:8080/api/hotels \
  -H "Authorization: Bearer <TOKEN>"
```

Ответ содержит список гостиниц, их идентификаторы, адреса и города.

### Шаг 3. Получение номеров гостиницы

Выберите `hotelId` из предыдущего ответа.

```http
GET http://localhost:8080/api/rooms/hotels/{hotelId}/rooms
Authorization: Bearer <TOKEN>
```

```bash
curl http://localhost:8080/api/rooms/hotels/<HOTEL_ID>/rooms \
  -H "Authorization: Bearer <TOKEN>"
```

В ответе возвращаются номера гостиницы, их идентификаторы, доступность и статистика бронирований.

Для следующего шага необходимо выбрать доступный номер и сохранить его `roomId`.

### Шаг 4. Создание бронирования

Запрос:

```http
POST http://localhost:8080/api/bookings
Authorization: Bearer <TOKEN>
Content-Type: application/json

{
  "userId": "<USER_ID>",
  "hotelId": "<HOTEL_ID>",
  "roomId": "<ROOM_ID>",
  "startDate": "2026-12-10",
  "endDate": "2026-12-15"
}
```

Пример через curl:

```bash
curl -X POST http://localhost:8080/api/bookings \
  -H "Authorization: Bearer <TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{
    "userId": "<USER_ID>",
    "hotelId": "<HOTEL_ID>",
    "roomId": "<ROOM_ID>",
    "startDate": "2026-12-10",
    "endDate": "2026-12-15"
  }'
```

`USER_ID`, `HOTEL_ID` и `ROOM_ID` должны соответствовать существующим записям. `USER_ID` должен принадлежать авторизованному пользователю.

Идентификатор пользователя можно получить непосредственно из базы данных:

```sql
SELECT id, username, role
FROM users
WHERE username = 'demo-user';
```

При успешной операции бронирование получает статус `CONFIRMED`.

### Шаг 5. Получение бронирования

Используйте идентификатор созданного бронирования:

```http
GET http://localhost:8080/api/bookings/{bookingId}
Authorization: Bearer <TOKEN>
```

```bash
curl http://localhost:8080/api/bookings/<BOOKING_ID> \
  -H "Authorization: Bearer <TOKEN>"
```

Также можно получить все бронирования текущего пользователя:

```http
GET http://localhost:8080/api/bookings/me
Authorization: Bearer <TOKEN>
```

### Шаг 6. Отмена бронирования

```http
POST http://localhost:8080/api/bookings/{bookingId}/cancel
Authorization: Bearer <TOKEN>
```

```bash
curl -X POST http://localhost:8080/api/bookings/<BOOKING_ID>/cancel \
  -H "Authorization: Bearer <TOKEN>"
```

После успешной отмены бронирование получает статус `CANCELLED`, а зарезервированный номер освобождается.

## 6. Процесс бронирования и Saga

Создание бронирования реализовано как распределённая операция с оркестрацией на стороне Booking Service.

Основные этапы:

1. Booking Service создаёт бронирование со статусом `PENDING`.
2. Booking Service отправляет запрос в Hotel Service на резервирование номера.
3. Hotel Service проверяет доступность номера и отсутствие пересекающихся бронирований.
4. При успешном резервировании Booking Service переводит бронирование в `CONFIRMED`.
5. При неуспешном резервировании выполняется компенсационное действие, освобождающее ресурс, а бронирование переводится в `CANCELLED`.

**Основные гарантии процесса:**

- Повторные запросы обрабатываются с учётом идемпотентности.
- Параллельные операции учитывают блокировки и доступность номера.
- Для пересекающихся интервалов бронирования действует проверка конфликта.
- Интервалы проживания задаются как `[startDate, endDate)`: дата выезда не входит в период проживания.
- При конфликте бронирования возвращается HTTP 409.
- Повторная отмена уже отменённого бронирования не выполняется повторно.

Пользовательская отмена подтверждённого бронирования является отдельной операцией и также освобождает зарезервированный номер.

## 7. Безопасность

Система использует JWT-аутентификацию и ролевую модель доступа.

- `USER` — просмотр гостиниц и номеров, создание и управление собственными бронированиями.
- `ADMIN` — административное управление гостиницами и номерами.
- JWT содержит идентификатор пользователя, имя пользователя и роль.
- Срок действия токена — 1 час.
- Booking Service и Hotel Service самостоятельно проверяют JWT.
- Внутренние служебные endpoints не публикуются через API Gateway и защищены отдельным механизмом внутренней авторизации.

## 8. Базы данных

Каждый бизнес-сервис использует собственную PostgreSQL базу данных.

| База данных | Назначение | Порт хоста |
|---|---|---:|
| `booking_db` | Пользователи и бронирования | 5432 |

Сервисы не обращаются напрямую к таблицам друг друга. Взаимодействие между бизнес-компонентами выполняется через API.

## 11. Тестирование

Booking Service содержит 30 модульных тестов, охватывающих бизнес-логику, оркестрацию Saga и работу с JWT-токенами.

### Матрица покрытия тестами

| Тестовый класс | Количество тестов | Покрытие |
|---|---:|---|
| `BookingServiceTest` | 9 | Создание бронирований, проверка дубликатов, подтверждение, отмена и получение бронирований |
| `SagaOrchestratorServiceTest` | 16 | Последовательность выполнения Saga, резервирование номеров, компенсационные действия, обработка ошибок, Circuit Breaker, границы транзакций и проверка дат |
| `JwtUtilTest` | 5 | Генерация JWT, извлечение данных из токена, проверка валидности и обработка срока действия |
| **Всего** | **30** | **Модульные тесты Booking Service** |

### Основные проверяемые сценарии

- Успешное создание бронирования: `PENDING → CONFIRMED`.
- Ошибка резервирования номера и выполнение компенсационного действия.
- Ошибка подтверждения бронирования и выполнение компенсационного действия.
- Обработка ошибки компенсации: `COMPENSATION_FAILED`.
- Отмена бронирования пользователем: `CONFIRMED → CANCELLED`.
- Работа Circuit Breaker при недоступности Hotel Service.
- Выполнение HTTP-запросов вне границ транзакций базы данных.
- Проверка JWT-токенов, включая недействительные и просроченные токены.


## 11. Результат

Проект реализует микросервисную систему бронирования гостиниц с централизованной маршрутизацией запросов, обнаружением сервисов, независимыми базами данных, JWT-аутентификацией и распределённым процессом бронирования на основе Saga.

Полный демонстрационный сценарий выполняется через API Gateway: авторизация пользователя, просмотр гостиниц и номеров, создание бронирования, проверка его статуса и отмена.
